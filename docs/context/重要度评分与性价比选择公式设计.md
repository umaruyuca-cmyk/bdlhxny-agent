# 重要度评分与性价比选择公式设计

状态：设计稿（对应《长上下文构建与压缩.md》第 7.4 节的落地细化）
代码位置：规划接入 `engine/src/bdlh_runtime/context/`（builder.py / models.py）

## 1. 目标和边界

当前 `budgeted` 策略的排序依据是条目上直接给出的标量 `priority`，分配依据是"公平份额 + 贪心"。本设计给出两个核心公式的完整定义：

- 公式五：重要度评分 `priority(item)`，把一条上下文条目的价值算成一个可解释的实数；
- 公式六：性价比选择值 `selection_value(item, representation)`，把"价值"和"占用 token"放在同一个分母上比较。

两个公式只使用条目自带的元数据（分类、来源、时间、引用关系），不调用外部模型，不训练参数。第一版权重为手工配置的常量，后续用对照评测（见第 9 节）校准。

### 1.1 不做什么

- 不用 LLM 给条目打分（LLM 只参与文本摘要表示，不参与排序）；
- 不做跨运行的学习或个性化（权重按场景版本固定，保证同一输入同一输出）；
- 不改变强制保留（REQUIRED）语义：公式只作用于 REQUIRED 之外的条目。

## 2. 公式五：重要度评分

### 2.1 总公式

```
priority(item) = wr·relevance + wa·authority + wf·freshness
               + wq·source_quality + wi·task_impact
               + wc·citation_dependency + we·failure_risk
               − ws·staleness
```

- 输出范围归一化到 `[0, 1]`（各因子本身在 `[0, 1]`，权重非负且和为 1，减法项单独处理，见 2.10）；
- 结果只用于条目之间的**相对排序**，绝对值没有业务含义；
- 同分时按 `(sequence, item_id)` 稳定排序，保证确定性。

### 2.2 因子定义

每个因子是 `[0, 1]` 上的实数，必须能从 `ContextItem` 现有字段或新增字段直接计算。

#### relevance（与当前任务的相关度）

条目与当前固定用例的匹配程度。

| 来源 | 取值 |
|---|---|
| 条目自带 `relevance` 字段（检索阶段产出） | 直接归一化使用 |
| 场景规则文件命中（如组合场景的"主要标的行情"） | 1.0 |
| 场景规则文件标记"通常省略"（无关记忆、无关新闻） | 0.1 |
| 无法判断 | 0.5（中性默认） |

第一版由场景规则文件给出离散档位（1.0 / 0.7 / 0.4 / 0.1），不做向量检索。

#### authority（来源权威度）

对应设计文档第 4.1 节的来源优先级，越高越可信。

| authority | 来源 |
|---|---|
| 1.0 | 系统规则、当前固定用例、登录身份 |
| 0.9 | 数据快照与工具返回的结构化事实（data-service） |
| 0.7 | 用户明确确认的约束与已确认记忆 |
| 0.5 | 模型从文本中提取的结论（带来源） |
| 0.2 | 新闻、网页、日志等外部文本 |

注意：authority 衡量"可信"，不衡量"重要"。一条外部新闻可以 relevance 高但 authority 低。

#### freshness（新鲜度）

数据时间距当前运行的接近程度，按条目类型设定半衰期：

```
freshness = 0.5^(Δt / half_life(type))
```

其中 `Δt` 为 `source_time` 到运行时刻的时间差。

| 条目类型 | 半衰期示例 | 说明 |
|---|---|---|
| market_observation | 5 分钟 | 行情过期极快 |
| news_evidence | 24 小时 | 新闻按天衰减 |
| portfolio_fact | 7 天 | 持仓结构变化慢 |
| fundamental_observation | 90 天 | 财务指标按季度 |
| user_profile / system_constraint | 不衰减，恒为 1.0 | |

#### source_quality（数据质量）

由数据质量条目（`data_quality` 类型）与条目自身状态共同决定：

| source_quality | 条件 |
|---|---|
| 1.0 | trust=verified 且无质量告警 |
| 0.7 | trust=unverified 但无冲突 |
| 0.4 | 存在过期标记（stale） |
| 0.1 | 存在缺失或冲突标记，且未解决 |

#### task_impact（任务影响度）

条目被当前用例验收条件或最终计算依赖的程度：

| task_impact | 条件 |
|---|---|
| 1.0 | 出现在用例的验收条件引用列表中 |
| 0.8 | 被预设多步用例的 `selected_facts` / 上一步 `result_refs` 引用 |
| 0.5 | 属于当前场景"优先保留"清单 |
| 0.2 | 属于当前场景"通常省略"清单 |

#### citation_dependency（被引用依赖）

条目被其他候选条目引用的程度（其他条目的来源指向它）：

```
citation_dependency = min(1, 被引用次数 / 3)
```

被 3 条及以上候选引用即封顶为 1.0。设计动机：一个被广泛依赖的中间事实（如某次估值结果）即使自身简短，丢失它会导致多条引用悬空，完整性检查失败。

#### failure_risk（失败风险）

条目携带的错误信息对当前任务的风险：

| failure_risk | 条件 |
|---|---|
| 1.0 | tool_failure 且属于当前用例主工具路径 |
| 0.7 | tool_failure（其他路径） |
| 0.4 | data_quality 高风险未解决 |
| 0.0 | 无失败信息 |

保留失败签名是防止 Agent 反复重试同一失败调用的关键，故给正向高分。

#### staleness（陈旧惩罚，减法项）

与 freshness 的区别：freshness 描述"数据本身的时间属性"，staleness 描述"相对当前任务已知的更新版本，这条是否已被取代"。

| staleness | 条件 |
|---|---|
| 1.0 | 已有同 source_ref 的新版本条目在候选集中（被取代） |
| 0.5 | 同一实体的另一来源更新（冲突待判） |
| 0.0 | 当前版本 |

### 2.3 权重按场景配置

权重不全局固定，按场景放在场景规则文件中，随 `context_profile_version` 进入缓存键。第一版初始值：

| 权重 | 行情 | 研究 | 组合 | 适合度 | 看护 | 拦截 | 知识 |
|---|---:|---:|---:|---:|---:|---:|---:|
| wr (relevance) | 0.25 | 0.25 | 0.20 | 0.20 | 0.25 | 0.15 | 0.30 |
| wa (authority) | 0.15 | 0.20 | 0.15 | 0.25 | 0.15 | 0.25 | 0.15 |
| wf (freshness) | 0.30 | 0.05 | 0.10 | 0.05 | 0.20 | 0.05 | 0.05 |
| wq (source_quality) | 0.10 | 0.15 | 0.15 | 0.15 | 0.15 | 0.10 | 0.10 |
| wi (task_impact) | 0.10 | 0.20 | 0.20 | 0.20 | 0.10 | 0.30 | 0.10 |
| wc (citation_dependency) | 0.05 | 0.10 | 0.10 | 0.10 | 0.10 | 0.05 | 0.10 |
| we (failure_risk) | 0.05 | 0.05 | 0.10 | 0.05 | 0.15 | 0.10 | 0.05 |
| 合计 | 1.00 | 1.00 | 1.00 | 1.00 | 1.00 | 1.00 | 1.00 |

配置约束（启动时校验，违反即拒绝构建）：

1. 各权重非负，`wr…we` 八项之和为 1（允许 ±0.001 浮点误差）；
2. `ws`（staleness）单独配置，上限 0.3，因为它是减法项，过大可能把高价值条目压成负分；
3. 任一场景至少有一个权重 ≥ 0.20，避免公式退化成纯平权。

### 2.4 归一化与裁剪

```
raw = wr·relevance + … + we·failure_risk − ws·staleness
priority = clamp(raw, 0, 1)
```

负值裁剪到 0 而不是保留负数：负分会让排序语义混乱（"比无关更无关"没有意义）。

### 2.5 计算示例

组合场景，一条 40 分钟前的持仓相关行情（`market_observation`，trust=verified，被 1 条候选引用，无失败）：

```
relevance=0.7, authority=0.9, freshness=0.5^(40/5)=0.002→按行情半衰期极低
```

这暴露了行情半衰期 5 分钟对组合场景过严——组合场景权重 wf=0.10 且该因子低，总分为：

```
0.20·0.7 + 0.15·0.9 + 0.10·0.002 + 0.15·1.0 + 0.20·0.5
+ 0.10·(1/3) + 0.10·0.0 − 0
= 0.140 + 0.135 + 0.0002 + 0.150 + 0.100 + 0.033 + 0 − 0
= 0.558
```

对比一条无关记忆（relevance=0.1，freshness 恒 1）：

```
0.20·0.1 + 0.15·0.7 + 0.10·1.0 + 0.15·1.0 + 0.20·0.2 + 0.10·0 + 0.10·0
= 0.020 + 0.105 + 0.100 + 0.150 + 0.040 = 0.415
```

行情仍胜出但优势不大，说明半衰期需要按场景微调（组合场景行情可用 2 小时），这正是第 9 节校准要解决的问题。

## 3. 公式六：性价比选择值

### 3.1 总公式

```
selection_value(item, representation) = priority(item) / representation_tokens(item, representation)
```

- 分子是公式五的输出；
- 分母是该条目在**某种具体表示方式下**渲染后的 token 数（含条目头部标记，与现有 `_render` 口径一致）；
- 单位含义：每 token 换来的重要度。

### 3.2 为什么需要它

公式五只回答"谁更重要"，不回答"谁更划算"。一条 priority=0.9、占 8000 token 的长新闻，和一条 priority=0.6、占 200 token 的结构化摘要，前者分高但性价比是后者的约 1/6。在预算紧张时，只按 priority 贪心会让大条目霸占预算（当前公平份额机制只能部分缓解）。公式六把"占用"放进分母，是预算受限下的标准做法（等价于性价比背包问题的贪心近似）。

### 3.3 与表示方式绑定

同一条件目有多种表示（完整内容 / 结构化摘要 / 文本摘要 / 引用 / 省略），各自的 token 数不同，因此 selection_value 是"条目 × 表示"的二元函数：

| 表示 | representation_tokens | 典型 selection_value 特征 |
|---|---|---|
| 完整内容 | 原文 token | 长，分母大，仅短小且关键时划算 |
| 结构化摘要 | 摘要 token | 通常最划算（确定性、保留数字） |
| 文本摘要 | LLM 摘要 token | 划算但有摘要成本和质量风险 |
| 引用 | 头部标记 token（约 10~20） | 分母极小，性价比恒高但信息量趋零 |
| 省略 | 0 | 不参与选择 |

引用表示的高性价比是一个陷阱：`priority/20` 几乎总是最大，若不约束会把一切降级为引用。因此第 4 节的选择算法对引用表示单独处理，不让它直接参与通用比较。

### 3.4 零除与下界

- `representation_tokens` 至少为头部标记的 token 数（现实现 `_render(item, "")` 恒非空），公式不除零；
- 对 `priority = 0` 的条目，selection_value 为 0，排在所有正分条目之后，与省略语义自然衔接。

## 4. 选择算法（两公式的使用方式）

替换 `_build_budgeted` 现有排序逻辑，流程如下：

```text
1. REQUIRED 全部原样放入（不变，超预算即失败）
2. 为每个非 REQUIRED 条目生成"可用表示"列表：
   完整内容（若很短）、结构化摘要、引用
   （文本摘要依赖 LLM，第一版仍不启用）
3. 生成所有 (item, representation) 对，计算各自的
   priority(item) 和 selection_value(item, representation)
4. 按 selection_value 降序遍历所有对：
   a. 跳过该条目已被更优表示选中的对
   b. 若选中的表示是"引用"，仅当该条目以其他表示放不下时才允许
   c. 放得下（≤ 剩余预算）→ 选中，扣减预算
   d. 放不下 → 尝试该条目更短的表示；全部放不下 → 省略
5. 依赖闭包：被选中条目引用的来源条目若被省略，
   至少以引用表示补入（保证引用不悬空）
6. 按原 sequence 排序输出，完整性检查（不变）
```

相对现状的变化：公平份额机制保留为兜底（步骤 4c 之外，单条目压缩目标仍受 fair_share 上限约束），但主排序从"priority 降序"改为"selection_value 降序"。

### 4.1 确定性保证

- 权重、因子、token 计数全部确定 → 同一输入同一输出；
- 同分冲突用 `(−selection_value, sequence, item_id, 表示优先级)` 字典序消解；
- 每个决定记录进 `ContextDecision.reason`，写明命中分数和表示，保证报告可解释。

## 6. 失败与降级

| 问题 | 处理 |
|---|---|
| 场景权重缺失 | 使用全局默认权重，报告记录 `weights_default=true` |
| 权重和不等于 1 | 启动校验失败，拒绝构建（不静默归一化） |
| source_time 缺失 | freshness 取 0.5 中性值， staleness 取 0 |
| 因子字段全部缺失 | priority=0，仅靠引用表示兜底 |
| 分数全为 0 | 退化为按 sequence 顺序的现行为，报告记录 |

## 7. 测试要点（tests/context/）

1. **权重校验**：和非 1、负权重、ws 超上限均拒绝；
2. **因子单测**：每个因子各档位取值正确，freshness 半衰期边界（Δt=0、Δt=half_life、Δt→∞）；
3. **排序决定性**：同输入重复构建 100 次结果逐字节一致；
4. **性价比语义**：构造"高优长文 vs 中优短摘"用例，验证 selection_value 排序与 priority 排序结果不同且前者预算利用率更高；
5. **引用陷阱**：验证引用表示不能凭低分母抢占完整/摘要表示的名额（规则 4b）；
6. **依赖闭包**：被选中条目的来源被省略时，引用表示自动补入，完整性检查通过；
7. **强制项隔离**：REQUIRED 条目不进入评分，不受任何权重影响；
8. **跨用户隔离**：他人条目在评分前已被隔离，不产生分数。

## 8. 报告与展示

每次运行的 `context_report` 增加分数表，网页展示用例中可回答"为什么这条新闻被省略"——展示其各因子值、总分、以及被选条目的性价比对比，而不是黑箱排序。

## 9. 权重校准与对照评测

公式上线后，权重初始值只是合理猜测，必须用第 13 节的对照框架校准：

- 固定 Agent 实现、模型、温度、工具数据和快照，仅变权重组合；
- 指标：任务完成率、关键事实保留率、working_tokens、压缩自身的额外成本（第一版为 0，无 LLM 摘要成本）；
- 每组权重的结果全部入库，`weights_version` 进入缓存键，避免不同权重共享缓存；
- 校准产生的权重变更走 `context_profile_version` 递增，旧运行可追溯当时权重。

## 10. 实施顺序

1. models.py 字段与 ScoringWeights、启动校验；
2. 评分器 `scoring.py`（纯函数，逐因子可单测）；
3. builder.py 接入 selection_value 排序与依赖闭包；
4. 报告与测试；
5. 评测跑权重网格，回填第 2.3 节初始值。
