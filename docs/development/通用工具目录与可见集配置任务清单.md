# 通用工具目录与可见集配置任务清单

依据 2026-08-21/22 所有者方向讨论生成,设计输入为《通用 Agent Mock Tools 评测设计》
(外部文档,经可行性核对)与现有架构。

**项目定位(所有任务的前提)**:本平台评测的是 **agent 执行指标**——工具选择、
幻觉、参数生成、权限判断、流程与检索——而不是工具调用本身。工具返回只是驱动
多轮决策的确定性反馈;**任何场景(包括对外演示)都不存在真实工具调用**,
没有"演示接真实工具"这回事。工具目录与可见集是实验变量,**把两者从代码常量
升格为可配置项**——评测全 mock、选取可配置、同题异勾选对照。
可与《核心功能任务清单》穿插执行(可见集落库若在其"统一运行工件"任务之后做更佳,但不阻塞)。

## 总体策略(所有任务共同遵守)

1. **全 mock 是唯一执行形态**:所有工具返回一律来自冻结表(fixture sets),
   不区分评测/演示场景——本项目不测工具执行质量,适配器槽(MCP/Java/web/
   deep_research)保持未装配,不存在真实调用路径;
2. **mock 只停在执行层**:冻结返回不打 `MOCK/TEST_FIXTURE` 质量标记,
   防止反 mock 防线(NON_PRODUCTION_DATA)误伤评测组;
3. **单一变量纪律**:每次对照只动一个旋钮(可见集/目录规模/装载策略),
   配置随批次落库、随工件记录,指标可归因;
4. **幻觉口径三分**:选错存在的工具 / 编造不存在的工具 / 调用目录内但本次
   不可见的工具——三个口径分开统计,不合并;
5. **写入工具 v1 只判不拦**:未确认写入由判官从调用记录判,引擎级确认门控属 v2;
6. DDL 与数据 SQL 一律写入 `db/postgresql/changes/` 交付所有者手动执行,
   代码不得直连库执行;验收用单元测试或事务内 dry-run 回滚;
7. **写代码前必须做"需求-代码一致性扫描"(硬性门禁,每个任务动手前执行)**:
   ①重读需求文档(《通用工具目录与Mock评测》+ 本清单对应任务卡 + 架构文档
   相关章节);②扫描全部相关代码的**最新**状态——注意仓库存在并行开发
   (《核心功能任务清单》的任务可能已改写 run_api/ab_eval/data 服务/工件结构,
   **必须以 `git log` 与当前代码为准,不得凭旧印象写代码**);③列出本次改动与
   现有逻辑的潜在冲突点(命名/请求字段/接口路径/指标口径/数据形状/落库字段),
   逐条给出处理方式;④冲突点与处理方式记入本清单修订记录后才开始写代码。
   发现需求文档与现有代码矛盾时,先在修订记录中写明取舍,不允许边写边改口径。

## GT-3 负例 mock 支持(空结果/失败/超时/部分成功)

**背景**:现有 18 条冻结全 SUCCESS;评测文档 §4.2 要求空数据/超时/部分成功/
参数错误路径;`FrozenObservations.__init__` 丢弃非 SUCCESS 行,负例进不去。

**第一步:旧初始化数据正反例审计**(动手改代码前完成,结论写进修订记录):
扫描 `db/postgresql/setup/init.sql` 的冻结数据段与库内现状,输出一张覆盖表——
每个工具 × {SUCCESS 正例, 空结果, FAILED, TIMEOUT} 是否有对应冻结行;
当前已知结论(以扫描复核为准):16 个金融工具在 `ab-eval` 仅有 SUCCESS 正例,
**零负例、零空结果**;`research.deep_search` 连正例都缺(GT-2 补)。
审计产出的缺口清单即本任务 SQL 的写入范围,不得只补示例性几条。

**后端设计**(查找语义保持"覆盖键优先、基准键回退"不变):

```python
# frozen_observations.py —— 构造时不再丢弃非 SUCCESS 行
self._by_key[call_key] = {"status": item["response_status"], "response": item["response"]}
# get() 命中后统一返回:
#   SUCCESS 行 → 原样返回 response(与今天完全一致)
#   非 SUCCESS 行 → {"status": <FAILED/TIMEOUT/ERROR>, **response}
#                    (失败信息进 Observation;不打 MOCK 质量标记)
# 空结果 = SUCCESS 行 + 空内容,零改动天然支持
```

**负例冻结集 SQL**(`20260822-fixture-negative.sql`,集 `ab-eval-negative-v1`):

```sql
-- 不存在代码:FAILED
('ab-eval-negative-v1',1,'market.get_realtime_quote:999999','market.get_realtime_quote',
 '{"symbol":"999999"}','FAILED','{"error":"symbol not found"}',...),
-- 超时:TIMEOUT(不做墙钟延迟,simulated_latency_ms 只记录)
('ab-eval-negative-v1',1,'market.get_news:000000','market.get_news',
 '{"symbol":"000000"}','TIMEOUT','{"error":"news source timeout"}',...),
-- 空结果:SUCCESS + 空内容
('ab-eval-negative-v1',1,'market.get_money_flow:000000','market.get_money_flow',
 '{"symbol":"000000"}','SUCCESS','{"net_inflow":null,"items":[]}',...)
```

**改动步骤**:
1. 引擎改动如上;ReAct 循环不动(失败回填后模型继续决策,正是被测行为);
2. 守卫调整:`test_frozen_fixture_sync` 的"全 SUCCESS"断言改为按 fixture set
   区分——ab-eval 仍须全 SUCCESS,负例集不做此断言;测试镜像 `frozen_fixtures.py`
   增加负例条目镜像;
3. 负例用例 SQL(可并入同一份):四类各 2 道(case_definitions/versions),
   `expected_checks` 示例:
   `{"category":"负例·空结果","expected_tools":["market.get_money_flow"],
     "expected_behavior":"report_empty"}` ——判官 v1 不新增行为断言,
   工具选对照常计分,空 Observation 下答案出现数字即被现有数字接地扣分;
4. 部分成功:同题两工具一 SUCCESS 一 FAILED(覆盖键组合),无需新机制。

**验收**:单元测试覆盖三类负例的查找与返回形状(FAILED/TIMEOUT/空内容);
现有 ReAct 失败回填测试仍绿;SQL 交付。

## GT-7 判官指标全量扩展

**背景**:现口径仅集合相等/目录外幻觉/越权;设计文档 §8 五组指标待落地;
金标需按用例写厚。

**指标公式**(全部确定性计算,输入=call_log/attempted/审计记录+金标):

```text
选择组(基于成功集合 S 与金标集合 G)
  precision = |S∩G|/|S|    recall = |S∩G|/|G|
  漏选 = recall<1 的运行占比   多余调用 = |S−G|>0 的运行占比
幻觉组(三分,不合并)
  目录外率 = attempted−目录    不可见率 = attempted−可见集(GT-4)
  禁止尝试率 = attempted ∩ absent_tools
参数与流程组
  参数完整率:必填参数齐全的调用占比(required_arguments)
  类型正确率:参数过 JSON Schema(jsonschema 库,能力行 parameters)的调用占比
  重复调用率:同 (name,args) 出现>1 次的运行占比
  顺序正确率:多步用例调用序 == expected_order(case_steps 金标)的运行占比
权限与确认组(v1 只判不拦)
  未确认写入率:调 side_effect≠none 工具且用例上下文无确认的运行占比
  查询误用写入率:只读题选中写入工具的运行占比
检索组(search_tools)
  命中率=检索结果含金标工具占比;无效检索率=不需要检索时检索的占比;
  重复检索率;检索后选择准确率;工具描述 token=当轮可见 schema 估算
```

**改动步骤**:
1. `RunJudgment` 扩字段+`_judge_*` 三函数按组计算;金标读取扩展
   `expected_checks`(expected_params/expected_order/expected_search/
   confirmation_present),未知金标键忽略并告警(向前兼容旧用例);
2. schema token 估算:当轮可见工具 parameters 序列化后 ConservativeTokenCounter;
3. `_agg_runs`/`_report_payload`/render_markdown 扩列;showcase results 页
   指标表增行随核心清单"七模块落地"一并(不阻塞本卡);
4. 测试:每指标一正一反(构造 call_log 金标);旧用例回归不破坏。

**验收**:engine 测试全绿;报告 JSON 新字段过既有 schema 校验(按需扩 schema)。
